# Synthetic best-gamma experiment on GRID

This experiment is independent of Meituan zoning. It uses heterogeneous origins and destinations in 2D, the selected existing synthetic geometry closest to the Meituan setup. It retains a uniform spatial law rather than fitting Meituan coordinates. The existing simulator and config runner suffice; no new policy implementation is needed.

## Initial experiment

| Setting | Value |
| --- | --- |
| Policy | Potential-augmented RBAT: `shadows=pb`, `dispatch=rbatch` |
| Potential | `gamma * direct_distance / 2`, with `tau=0` |
| Gamma | 0, 0.1, ..., 1.0 |
| Pooling window d | 5, 10, 15, 20, 25, 30 |
| Jobs per instance | 1,000 |
| Geometry | Heterogeneous origins and destinations in the 2D unit square |
| Spatial law | Beta(1, 1), i.e. uniform, as generated by the current CLI |
| Arrivals | One per time unit, at times 1, 2, ..., n |
| Training seeds | 1 through 100 |
| Evaluation seeds | 101 through 200 |
| Offline OPT | Disabled for the initial sweep |

The downloaded synthetic configs use 100 seeds. This experiment retains that replication count for training and adds 100 independent evaluation seeds. Each split has **6,600 jobs** on GRID: 100 seeds × 6 windows × 11 gammas. Every task writes one simulation row. The same seed regenerates identical jobs for every gamma and window, enabling paired comparisons. Nominal density is d; the end of the finite arrival horizon limits future opportunities for the last jobs.

Gamma 0.2 means an effective distance coefficient of 0.1. Keep those labels distinct in plots. `rbatch+` is a different policy and is not used here.

## Submit through anapy3

These commands run on GRID after uploading. They use the syntax documented in `Intro_to_GRID_2022.pdf`, slides 35–36 and 62: GRID options precede Python options, and `--grid_array=first-last/concurrency` limits concurrent tasks. Slide 54 explains why submitting from a timestamped directory keeps that submission's logs together. The reference is historical; it is not a statement of current account quotas.

Set the checkout location and make the uploaded source available to Python:

```bash
DDP_GRID_REPO="/user/mer2262/ddp_pkg_release"
DDP_CONFIG="$DDP_GRID_REPO/configs/synthetic_gamma_heterogeneous_2d_v1_heterogeneous_2d_n1000_a1_b1_train.csv"
export PYTHONPATH="$DDP_GRID_REPO/src${PYTHONPATH:+:$PYTHONPATH}"
```

The `PYTHONPATH` setting selects the uploaded source tree when the submission runs from a log directory. It also propagates to the Python subprocess launched by `run_from_config`. The config's absolute path controls result placement. The pilot confirms this setup in the actual `anapy3` environment.

Start with the first seed across all six windows and all eleven gammas, including the largest window:

```bash
DDP_LOGDIR="$DDP_GRID_REPO/logs/gamma-2d-train-pilot-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$DDP_LOGDIR"
cp "$DDP_CONFIG" "$DDP_LOGDIR/submitted_config.csv"

(
  cd "$DDP_LOGDIR" || exit 1
  anapy3 --grid_submit=batch --grid_mem=8G --grid_ncpus=1 \
    --grid_array=1-66/11 \
    -m ddp.scripts.run_from_config \
    --config "$DDP_CONFIG"
)
```

This submits 66 tasks with at most 11 running concurrently. Each config has 6,600 rows, not 600: 100 seeds × 6 windows × 11 gammas. Task IDs refer to one-based data rows, excluding the CSV header.

After the 66 pilot tasks pass validation, submit all remaining work with one concurrency cap of 1,000 tasks. The command below creates a timestamped combined config on GRID from the two uploaded CSVs. It includes training rows 67–6600 (6,534 tasks) and all 6,600 evaluation rows, for 13,134 tasks total. Existing `save_csv` values preserve the separate training and evaluation result directories.

```bash
(
  set -e
  DDP_GRID_REPO="/user/mer2262/ddp_pkg_release"
  DDP_PREFIX="$DDP_GRID_REPO/configs/synthetic_gamma_heterogeneous_2d_v1_heterogeneous_2d_n1000_a1_b1"
  DDP_RUN_TAG="gamma-2d-full-$(date +%Y%m%d-%H%M%S)"
  DDP_CONFIG="${DDP_PREFIX}_${DDP_RUN_TAG}.csv"
  DDP_LOGDIR="$DDP_GRID_REPO/logs/$DDP_RUN_TAG"

  {
    head -n 1 "${DDP_PREFIX}_train.csv"
    tail -n +68 "${DDP_PREFIX}_train.csv"
    tail -n +2 "${DDP_PREFIX}_eval.csv"
  } > "$DDP_CONFIG"
  if [ "$(wc -l < "$DDP_CONFIG")" -ne 13135 ]; then
    echo "Expected 13134 data rows plus a header; check the uploaded configs."
    exit 1
  fi

  export PYTHONPATH="$DDP_GRID_REPO/src${PYTHONPATH:+:$PYTHONPATH}"
  mkdir -p "$DDP_LOGDIR"
  cp "$DDP_CONFIG" "$DDP_LOGDIR/submitted_config.csv"
  cd "$DDP_LOGDIR"
  anapy3 --grid_submit=batch --grid_mem=8G --grid_ncpus=1 \
    --grid_array=1-13134/1000 \
    -m ddp.scripts.run_from_config \
    --config "$DDP_CONFIG"
)
```

The generated source CSVs contain one record per line. Line 68 of the training CSV is data row 67, so the command excludes exactly the completed pilot. The combined array's task 1 is training seed 2, d=5, gamma=0; task 6534 is training seed 100, d=30, gamma=1; task 6535 is evaluation seed 101, d=5, gamma=0; task 13134 is evaluation seed 200, d=30, gamma=1. Use the combined config's row numbers when resubmitting individual tasks.

The `/1000` cap applies to this entire array. It is a maximum, with new tasks eligible to start as slots become available; GRID account limits and available resources may keep actual concurrency lower. Two independent arrays each capped at 1000 could run 2000 tasks, which is why this workflow combines the splits. Submit the combined array once and do not overlap it with separate training/evaluation submissions for the same output files. Keep the submitted config and source fixed while the array is active. The log-directory config is an audit copy only; `--config` must point to the file under `configs/` for correct repository-root resolution.

Check the queue:

```bash
qstat -u mer2262
```

Eight GB per task remains the request used for the successful pilot; peak memory was not included in the downloaded result CSVs. The primary workflow uses `anapy3` and its configured Anaconda interpreter. If switching to a private Python environment, use the documented `grid_run` route with that interpreter instead of assuming conda activation changes `anapy3`.

## Check the pilot and results

Use `qstat` or `qstat -j JOB_ID` to inspect the submission. Each task's log should report its selected row and command. Check for `--het-origins --dimension 2`, PB-RBAT, the expected gamma/window/seed, and a result path under the GRID checkout. Row 1 should be seed 1, d=5, gamma=0; row 66 should be seed 1, d=30, gamma=1. Confirm all 66 pilot result files before launching rows 67 onward.

Record the submitted job IDs with the log directories. Completed task failures can be investigated using the slides' bounded accounting pattern, e.g. `qacct -o mer2262 -d 2 -j JOB_ID`. Successful completion has `failed=0` and `exit_status=0`; missing CSVs or nonzero statuses need inspection and rerunning the affected task IDs. Preserve those IDs so reruns address the same config rows.

Results are written below the GRID checkout:

```text
results/synthetic_gamma_heterogeneous_2d_v1/heterogeneous_2d_n1000_a1_b1/train/
results/synthetic_gamma_heterogeneous_2d_v1/heterogeneous_2d_n1000_a1_b1/eval/

# Example distinct files:
train/seed000001_d5_g0p1.csv
train/seed000001_d5_g1.csv
```

Every output contains seed, n, d, gamma, tau, savings, pooled percentage, pair/solo counts, LP ratio and policy runtime. Split and geometry are recorded in the config and directory path. Preserve the manifest when copying outputs back. Failed tasks can be resubmitted by their one-based config row number; do not run two copies of the same row concurrently.

The existing runner **still solves the LP for every candidate**, even for PB alone. `with_opt=0` avoids an additional OPT computation but does not skip LP. The sweep therefore repeats LP work across gammas. This version deliberately reuses the established runner so GRID can start immediately; benchmark actual total walltime in the pilot before selecting queue resources. The output `time_s` measures the policy and excludes the LP stage. If LP becomes a bottleneck, a later grouped runner can prepare each seed/window once without changing the experiment.

Preparation checks on 2026-09-08 verified complete grids, 13,200 unique output paths, disjoint seed splits, and explicit `--het-origins --dimension 2` flags. The new output namespace does not overlap the earlier common-origin experiment. Three n=24 runs at gamma 0, 0.5 and 1 used identical generated job arrays; both coordinates varied for origins and destinations, and all result rows accounted for every job. A local heterogeneous-origin 2D benchmark at n=1000, d=30, gamma=0.5, seed=1 completed in **12.35 seconds**: 3.03 seconds for LP and 9.02 seconds for the policy. It saved 134.179 distance units with 382 pairs. This is a local measurement for one instance, not a GRID runtime prediction.

Additional local dry-runs from an unrelated temporary log directory verified rows 1, 66, and 6600, uploaded-source selection through `PYTHONPATH`, and result paths under the config's repository root. The `anapy3` scheduler wrapper is available on GRID only and was not executed locally; no GRID jobs were submitted during preparation.

Downloaded pilot validation on 2026-09-09 passed for all 66 expected files, with one result row per file and no missing or unexpected CSVs. Parameters match the first 66 training config rows; all required metrics are finite; every result satisfies `2 * pairs + solos = 1000`; pooled percentages and LP ratios/gaps are consistent; and each window has the same inferred LP bound across all 11 gammas. Fresh local reproductions at (d=5, gamma=0) and (d=30, gamma=1), plus the earlier local benchmark at (d=30, gamma=0.5), match every non-timing result field within 1e-8 tolerance. The downloaded policy runtimes range from 1.64 to 13.64 seconds and exclude LP computation. Both full configs contain 6,600 rows with disjoint training/evaluation seeds and 13,200 unique output paths. This checks result contents and reproducibility; GRID scheduler accounting and peak memory were not downloaded.

## Selection and figures after the runs

For each geometry and d, maximize mean savings over the 100 training seeds. Use an explicit deterministic rule for exact ties (for example, the smallest maximizing gamma), and retain the whole curve and near-optimal range. Evaluate that selected gamma on seeds 101–200. Compare against gamma=0, gamma=0.5, and any other fixed reference using the same evaluation seeds. Do not choose a different best gamma for each evaluation seed or select the deployed gamma using evaluation averages.

Keep individual seed rows when joining outputs. Check for all 11 gammas for every seed/window before fitting. Initial plots are training mean savings versus gamma for each d, selected gamma versus d, and held-out paired savings differences versus fixed gamma references. The plotting/fitting step is a subsequent analysis; this change prepares and verifies the simulation configs.

## Optional geometries and distributions

The primary experiment uses heterogeneous origins in 2D. The generator also accepts common-origin 1D/2D and heterogeneous-origin 1D geometries, without legacy flags:

```bash
python scripts/generate_synthetic_gamma_config.py \
  --experiment-id synthetic_gamma_geometries_v1 \
  --geometries common_origin_1d,common_origin_2d,heterogeneous_1d,heterogeneous_2d
```

This generates a train/eval pair of 6,600-row configs for each geometry. Submit the exact desired filename, not a wildcard. Beta alternatives can be declared with `--beta-alpha` and `--beta-beta`; use a distinct experiment ID to preserve the original manifest. Do not combine geometries when selecting a best gamma unless that is a separately declared research question.

## Optional direct-SGE submission

The existing `scripts/run_synthetic_gamma_grid.sh` supports direct `qsub` when an appropriate GRID Python interpreter and scheduler resource settings have been selected explicitly. It is not used in the primary `anapy3 -m ddp.scripts.run_from_config` workflow above.

For this alternative, upload the shell runner, submit from the checkout root, set `DDP_PYTHON` to the chosen GRID interpreter, and use the site's appropriate memory/queue options. The runner resolves the checkout from `DDP_PROJECT_ROOT`, then `SGE_O_WORKDIR`, then its own file location for local use. The SGE source-directory fallback was tested with a spooled copy of the script. Use the established `anapy3` commands above unless a different interpreter or scheduler setup is specifically needed.
